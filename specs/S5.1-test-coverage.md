# Cobertura de Testes — Endpoints e Regras de Negócio

## User Value
Como PM/desenvolvedor, quero que todos os endpoints da API e regras de negócio
tenham testes de integração/unitários abrangentes para garantir que o MVP funcione
corretamente em produção sem regressões.

## Contexto
O projeto já possui testes de serviço (`Infrastructure.Tests`) e E2E (Playwright),
mas faltam testes de integração no nível de endpoint (HTTP) que validem status
codes, auth e contratos sem depender de um navegador. A cobertura mínima no CI
é 55% — precisa subir para refletir o estado real do MVP.

## Acceptance Criteria
1. Criar um projeto de testes de integração `ResponsabiliMano.Web.IntegrationTests`
   usando `WebApplicationFactory<Program>` (ou a classe de ponto de entrada
   equivalente) com SQLite in-memory ou Testcontainers PostgreSQL.
2. Testar cada endpoint REST com pelo menos um caso happy-path e um caso de erro:
   - `POST /api/auth/register-and-login` — sucesso (201 + cookie), e-mail duplicado (400).
   - `POST /api/auth/login` — sucesso (200 + cookie), credenciais inválidas (401).
   - `POST /api/auth/forgot-password` — sucesso (200), e-mail inexistente (200, sem leak).
   - `POST /api/auth/reset-password` — sucesso (200), token inválido (400).
   - `GET /api/projects/{id}` — sucesso (200), não-participante (403), inexistente (404).
   - `POST /api/projects` — sucesso (201), inválido (400).
   - `POST /api/projects/{id}/invite` — sucesso (200), não-criador (403).
   - `POST /api/projects/{id}/approve` — sucesso (200), já aprovado (400).
   - `POST /api/projects/{id}/change-requests` — sucesso (200), dados inválidos (400).
   - `POST /api/projects/{id}/change-requests/{crId}/respond` — sucesso (200),
     não-participante (403).
   - `POST /api/projects/{id}/checkins` — sucesso (200), duplicado (400),
     não-participante (403), projeto não-ativo (400).
   - `GET /api/projects/{id}/dashboard` — sucesso (200), flag off (404),
     não-participante (403).
   - `POST /api/cron/checkins/dispatch` — sem secret (401), com secret (200).
   - `POST /api/cron/checkins/reminders` — sem secret (401), com secret (200).
3. Testar o fluxo de change-request end-to-end no nível de serviço: criar proposta
   → aprovar → verificar que a mudança foi aplicada no projeto (data de fim,
   frequência, metas). Já existe em `ProjectServiceTests` mas deve ser completado
   se faltar cobertura para `RespondToChangeRequestAsync` com `Approved` e `Rejected`.
4. Testar `UserLoginService` para: credenciais válidas (retorna user), senha errada
   (retorna null), usuário inexistente (retorna null). Já existe parcialmente em
   `UserLoginServiceTests` — completar edge cases se faltar.
5. Elevar o threshold de cobertura no CI de `55 80` para `65 80` (mínimo de 65%
   de line coverage). Se a cobertura atual já for superior, ajustar para o valor
   atual arredondado para baixo (never lower the bar).
6. Todos os testes novos passam com `dotnet test` (excluindo E2E) e o CI fica verde.

## Data Model
- Sem mudança. Os testes usam o schema existente via `TestDbContextFactory` (SQLite
  in-memory) ou `WebApplicationFactory` com SQLite.

## Security Constraints
- Testes de integração não usam credenciais reais — usuários de teste são seedados
  com senhas hash via `PasswordHasher.Hash`.
- O teste de `forgot-password` com e-mail inexistente verifica que a resposta é
  200 (não vaza quais e-mails estão cadastrados).
- Nenhum secret real nos testes; o `X-Cron-Secret` de teste é um valor fixo e
  documentado.

## API / Event Contract
Os testes de integração validam conformidade com `contracts/responsabilimano-api.yaml`
(status codes, auth, schemas de resposta). O gate de conformidade de contrato
(`scripts/contract-conformance.py`) já roda no CI e não é alterado por esta spec.

## Dependencies
- Nenhuma. Pode ser executada independentemente das outras specs da Sprint 5.

## Out of Scope
- Testes E2E adicionais com Playwright (já cobertos em `Web.E2ETests`).
- Testes de carga/performance.
- Testes de acessibilidade (WCAG).
- Mock de serviços externos (SMTP real não é testado em integração).

## Verification
- `dotnet test --filter "FullyQualifiedName!~ResponsabiliMano.Web.E2ETests"`
  verde com todos os novos testes.
- `dotnet test --filter "FullyQualifiedName!~ResponsabiliMano.Web.E2ETests"
  --settings coverage.runsettings --collect:"XPlat Code Coverage"` produz
  cobertura ≥ 65% em `Core` + `Infrastructure`.
- O gate de cobertura no CI (`irongut/CodeCoverageSummary` com thresholds `65 80`)
  passa.
