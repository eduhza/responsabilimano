# Tipos de meta booleano e escala

## Contexto
`GoalDataType` só tem `Decimal`, `Integer` e `Percent` — todos numéricos contínuos.
Isso empurra o produto para metas físicas e torna desconfortáveis os objetivos que o
PM quer suportar: "estudei hoje?", "fiz o simulado?", "quão focado eu estive nesta
semana?". Além disso a renderização é fixa: `CheckInEditor` sempre desenha um campo
numérico, ignorando o `DataType`.

## User Value
Como usuário com metas de estudo, concurso ou carreira, quero registrar
"sim/não" e notas em escala, para acompanhar hábitos e avaliações subjetivas com a
mesma mecânica de check-in e dashboard.

## Acceptance Criteria
1. `GoalDataType` ganha `Boolean` e `Scale`. **Sem mudança no esquema das métricas**:
   `CheckInMetric.Value` continua `decimal` — `Boolean` grava `0` ou `1`; `Scale`
   grava um inteiro dentro de `[MinValue, MaxValue]`.
2. Validação server-side em `CheckInService.ValidateMetrics` (estendendo o AC 6 do X2):
   `Boolean` aceita **somente** `0` ou `1`; `Scale` aceita somente inteiro em
   `[MinValue, MaxValue]`. Fora disso → `ArgumentException` com mensagem localizada.
3. Validação de definição de meta em `ProjectService`: `Boolean` força
   `MinValue = 0`, `MaxValue = 1` e `Unit` opcional (vazia é válida — "Estudei hoje?"
   não tem unidade); `Scale` exige `MinValue`/`MaxValue` inteiros com
   `MaxValue > MinValue` e sugere `1..5` por padrão.
4. Novo `Design/RmGoalValueInput.razor` despacha o controle pelo `DataType` e é o
   **único** ponto de entrada de valor de meta no check-in:
   - `Boolean` → switch Sim/Não;
   - `Scale` → botões segmentados de `Min` a `Max`;
   - `Integer` → stepper (`−`/`+`);
   - `Percent` → slider + campo numérico sincronizados;
   - `Decimal` → `RmNumberInput` (X2).
   Todos com `aria-label` e navegação por teclado.
5. Novo `Shared/GoalValueDisplay.razor` formata a exibição pelo `DataType` e é usado
   em `ProjectDetail` (tiles), `InvitationAccept`, tela de negociação (S7.3),
   `GoalChangeDiff` e dashboard: `Boolean` exibe "Sim"/"Não" (nunca `1`/`0`),
   `Scale` exibe `4 / 5`, `Percent` exibe `85 %`, decimais em pt-BR.
6. Agregação correta no dashboard, por tipo:
   - `Boolean` → **taxa de cumprimento** (% de períodos com valor `1`) e sequência,
     nunca média aritmética;
   - `Scale` → média com uma casa decimal, escala fixa `Min..Max` no gráfico;
   - demais tipos → comportamento atual.
7. `GoalDirection` (S7.2) para `Boolean` é sempre `Reach` com alvo `1`; para `Scale`
   aceita `Increase` ou `Reach`. Combinações inválidas são rejeitadas no serviço.
8. O seletor de tipo do wizard (`CreateProject`) e o da negociação passam a listar os
   5 tipos com rótulos e ajuda contextual localizados; ao trocar o tipo, os campos
   irrelevantes (unidade, min, max) somem ou se preenchem sozinhos.
9. Retrocompatibilidade: projetos e check-ins existentes com os 3 tipos antigos
   continuam funcionando sem migration de dados. A migration é apenas de enum
   (valores inteiros novos), sem alterar linhas existentes.
10. Todos os textos visíveis em `AppStrings.resx` e `AppStrings.pt-BR.resx`.

## Data Model
- `GoalDataType` (enum, persistido como `int`): `Decimal=0, Integer=1, Percent=2,
  Boolean=3, Scale=4`. **Os valores existentes não mudam** — os novos são apenas
  acrescentados no fim, para não reinterpretar dados gravados.
- Sem nova tabela e sem alteração de coluna. Nenhuma migration de dados.

## Security Constraints
- Toda restrição de tipo é reaplicada no servidor (AC 2/3); o controle de UI é
  conveniência. Um cliente que poste `Value = 7` numa meta booleana recebe 400.
- Sem PII em log; a validação registra o `goalFieldId` e o tipo, não o valor.

## API / Event Contract
Ver `contracts/responsabilimano-api.yaml`: o enum `GoalDataType` nos schemas
`GoalField` / `GoalFieldRequest` ganha `Boolean` e `Scale`. Mudança **aditiva** e
retrocompatível.

## Dependencies
- X2 (`RmNumberInput`, validação por tipo no servidor).
- S7.2 (`GoalDirection` e alvo por participante, referenciados nos AC 6/7).

## Out of Scope
- Tipos "checklist/marco", "contagem" e "duração" — descartados nesta rodada pelo PM.
- Campo de texto livre no check-in.
- Biblioteca de modelos de meta por tema — spec S7.5.
- Gráfico dedicado para booleano (heatmap de semanas): o dashboard mostra taxa +
  sequência; visual mais rico fica para spec futura.

## Verification
- `dotnet build ResponsabiliMano.slnx` e `dotnet test` verdes.
- `python scripts/contract-conformance.py` verde (enum ampliado).
- Testes: `CheckInServiceTests` para AC 2 (`Boolean` com `0.5` e `2` rejeitados;
  `Scale` com `3.5` e fora do intervalo rejeitados); `ProjectServiceTests` para AC 3
  e AC 7; `DashboardServiceTests` provando que booleano agrega como **taxa** e não
  como média (ex.: `1,0,1,1` → 75%, não 0,75 exibido como média de kg);
  bUnit em `RmGoalValueInput` (um caso por tipo) e em `GoalValueDisplay`
  (`Boolean` renderiza "Sim", nunca "1").
- Teste de guarda dos valores do enum (AC/Data Model): assevera
  `(int)GoalDataType.Decimal == 0 … Percent == 2`, para que ninguém reordene o enum
  e reinterprete dados gravados.
- Manual/E2E: criar projeto "Concurso" com metas "Horas de estudo" (Decimal, h),
  "Questões resolvidas" (Integer), "Simulado feito?" (Boolean) e "Foco na semana"
  (Scale 1–5); fazer check-in e conferir o dashboard.
