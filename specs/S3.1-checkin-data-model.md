# Modelo de dados de check-in

## User Value
Como sistema, preciso persistir check-ins periódicos por usuário/projeto para
alimentar lembretes e o dashboard comparativo.

## Acceptance Criteria
1. Entidade `CheckIn` { Id, ProjectId, UserId, Feeling, SubmittedAt, PeriodNumber }.
2. Entidade `CheckInMetric` { Id, CheckInId, GoalFieldId, Value(decimal) }.
3. Constraint única: um check-in por (ProjectId, UserId, PeriodNumber).
4. Migration EF Core com tabelas/colunas em lowercase/snake_case e FKs indexadas.
5. `SubmittedAt` persistido como UTC (`DateTimeKind.Utc`) — requisito Npgsql.
6. Testes de domínio/persistência: criação, unicidade por período, cascade de
   `CheckInMetric` ao remover `CheckIn`.

## Data Model
- CheckIn (novo) e CheckInMetric (novo), ligadas a Project, User e GoalField.

## Security Constraints
- Sem PII em logs. (Camada de dados; auth entra em S3.2.)

## API / Event Contract
- none (persistência). O endpoint entra em S3.2.

## Dependencies
- Projeto em status "Em Andamento" (Sprint 2, concluída).

## Out of Scope
- Tela de check-in (S3.2), cronjob (S3.3), lembretes (S3.4).

## Verification
- `dotnet test` cobrindo unicidade por período e cascade.
- Migration aplica limpa em banco novo.
